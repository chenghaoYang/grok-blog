# 第 9 集：在一起更好还是分开更好？

大家好，欢迎收听《软件设计的哲学》。今天我们讨论软件设计里最基础也最常遇到的问题：给定两个功能，它们应该放在同一个地方一起实现，还是拆开到不同地方？[pause] 这个选择从方法、类到服务层级都适用。目标始终是降低整个系统的复杂度，同时让模块化程度更高。

先来看看为什么一味细分不一定是好事。很多人觉得把系统切成很多小组件，每个组件就简单了。但细分本身会制造新的复杂性。组件数量一多，追踪起来就费劲，找东西也难；新接口随之增加，每个接口都带来额外负担；管理多个对象的代码也会多出来；最麻烦的是分离效应——原本在同一个类里的方法被拆到不同文件后，开发者得来回跳转，如果它们之间有依赖，就很容易忽略关键联系，导致缺陷；重复代码也容易出现，原本一次就能搞定的逻辑，现在每个拆分后的组件都要复制一份。

判断两段代码是否该组合，关键看它们是否紧密相关。它们是否共享同一信息？是否总是被一起调用？在概念上是否属于更高层的同一类别？或者不看其中一段就很难理解另一段？如果这些信号都存在，组合起来最有利；反之，如果只是单向依赖，或者组合后接口反而变复杂，那就该分开。

以 HTTP 服务器为例。早期实现里、读取网络套接字文本和解析请求格式被放在两个不同类的方法里。读取方法虽然不负责完整解析，但要判断请求结束位置，就必须理解标头语法；解析方法同样依赖请求格式知识。结果两个类都对 HTTP 格式有了重复了解，代码又长又绕。合并后，中间传递字符串的接口消失了，整个流程在一个地方完成，代码明显变短变简单。这就是信息共享推动组合的典型好处。

再看简化接口的机会。Java I/O 库里，如果把 FileInputStream 和 BufferedInputStream 合并，默认提供缓冲，大多数用户甚至不用知道缓冲机制存在。只有少数需要自定义缓冲的场景，才会用到额外方法。组合后的类接口更浅，用户用起来更直接，底层细节被自动处理了。

消除重复也是组合的重要理由。书里有一张图，展示处理不同网络数据包时，短包错误日志的代码在多个 case 分支里重复出现。改用 goto 把日志语句集中到方法末尾，只保留一个副本，既去掉了嵌套，又避免了多处维护。前提是这种用法要克制，否则会带来可维护性问题。

不过，通用机制和专用代码必须分开。文本类应该只提供通用的插入、删除等操作，删除选中区域这种界面专用逻辑就该留在用户界面模块里，否则会造成信息泄露：未来界面需求一变，底层文本类也得跟着改，依赖关系就乱了。

我们来看两个具体对比案例。第一个是图形界面编辑器里的插入光标和区域选择。光标总是位于选区一端，点击拖拽时两者同时变化，插入文本前还要先删除选区，看起来很相关。有人试着用一个对象存储两个位置和两个布尔值，结果上层代码还是得分别调用方法来操作选区和光标，实现却更尴尬：要判断布尔值才能知道光标到底在选区起点还是终点。分开后，用 Position 类分别表示位置，选区用两个 Position，光标用一个，接口简单直接，还能在项目其他地方复用。这个例子也说明，关联度不够时强行组合只会增加间接性。

第二个案例来自学生项目的错误日志。一个类里到处是这样的序列：捕获 IOException 后调用 NetworkErrorLogger 的方法记录细节。那个日志类定义在同一文件末尾，每个方法如 logRpcSendError 只有一行代码，却需要大段文档说明参数。每个方法只在一个地方被调用，阅读调用方代码的人往往要跳过去确认记录了什么，反过来也一样。移除这些浅方法，把日志语句直接写回错误检测处后，代码更连贯，接口和文档负担都消失了。

方法层面的拆分同样遵循相同原则。很多人以为方法超过二十行就该拆，但长度本身很少是充分理由。拆分会引入新接口，如果子任务和父方法之间存在复杂交互，读者就得来回跳转理解两者如何协作。只有当拆分能产生更清晰抽象时才值得做：把独立子任务抽成子方法，父方法调用它，双方都能单独理解；或者把原来复杂的接口拆成两个更专注的方法，让调用者不必同时处理两者。如果拆完后调用者还得在多个浅方法间传状态，或者出现“连体方法”——必须一起读才能懂，那就该合并回去。长方法只要每个部分相对独立，或者交互紧密需要同时看到，就没必要拆。深度比长度更重要：接口要远比实现简单。

带走今天的核心：组合还是分开，始终围绕是否真正降低系统复杂度、提供更深接口和更好信息隐藏来判断。下一集我们继续探讨模块设计的其他权衡思路。
