# 第 20 集：性能设计

大家好，欢迎收听《软件设计的哲学》。今天我们来谈谈性能设计这个话题。很多人在写代码时，一想到要让系统跑得更快，就容易走极端，要么每条语句都拼命优化，要么干脆完全不管性能，等到系统慢得让人着急再回头补救。其实这两条路都不理想，我们今天就聊聊怎么在保持设计简洁的前提下，把性能也照顾好。[pause]

到目前为止，我们讨论的软件设计重点都在降低复杂性上，让系统更容易理解。但如果必须让系统运行得更高效，性能考虑该怎么融入设计过程呢？本章的核心观点仍然是简单性：简单不仅能改善设计，通常还能让系统本身更快。解决性能问题的第一步，是问自己在正常开发里到底该在多大程度上担心性能。如果你试图把每一条语句都榨到最快，开发速度会变慢，还会引入很多不必要的复杂性。而且很多所谓的优化其实对性能没什么帮助。反过来，如果你完全忽略性能，就很容易在整个代码里留下大量低效的实现，最后系统可能比实际需要慢五到十倍。到那时再想优化就很难了，因为没有单一改动能带来明显效果。

最好的做法是走中间路线。你可以利用对性能的基本认识，选择那些“自然高效”同时又整洁简单的设计方案。关键在于意识到哪些操作从根本上就开销很大。今天仍然比较重的操作包括网络通信、辅助存储的 I/O、动态内存分配，以及缓存缺失。网络往返即使在数据中心内也要十到五十微秒，相当于执行几万条指令；广域网则可能达到十到一百毫秒。磁盘 I/O 需要五到十毫秒，闪存也要十到一百微秒。malloc 或 new 这样的分配操作涉及大量额外开销，而缓存缺失同样会拖慢整体性能。了解这些代价的最好办法是运行微基准测试，RAMCloud 项目就专门做了一个简单框架，花几天时间搭建好后，添加新测试只需五到十分钟，最终积累了几十个基准，帮助他们快速判断现有库和新代码的真实性能。

有了这些基本认识后，你就能在日常选择中偏向开销小的方案。比如存储大量需要键值查找的对象时，哈希表和有序映射都简单易用，但哈希表通常快五到十倍。除非你确实需要有序属性，否则直接选哈希表就行了。再比如用 C 或 C++ 分配结构数组，把结构直接放在数组里，只需一次大块内存分配，比先分配指针数组再逐个分配结构要高效得多。这些选择都不需要牺牲可读性，却能自然提升性能。

如果更快的方法会增加复杂性，判断就更难了。当增加的复杂性很少，而且被隐藏在接口之后时，或许值得尝试，但要小心复杂性是慢慢累积的。如果更快的设计会让接口变复杂，或者大幅增加实现难度，那就先从简单方案开始，等性能真的成为问题再优化。RAMCloud 项目里有个例子，他们为了把数据中心网络访问的延迟压到最低，决定使用特殊硬件让系统绕过内核直接收发数据包。这个决定增加了复杂度，但他们之前已经测量过基于内核的网络太慢，所以值得做。项目其余部分则保持了简单设计，把这个大问题解决后，其他事情反而更容易了。

简单代码往往比复杂代码跑得更快，因为你已经通过定义避开了特殊情况，就不需要额外检查代码，系统自然更快。深类也更高效，因为每个方法调用完成的工作更多，减少了层级切换带来的开销。[pause]

不过即使你按上面方式设计，系统还是可能不够快。这时候千万不要凭直觉乱改。程序员对性能的直觉不可靠，即使是有经验的开发者也一样。正确的做法是先测量系统的现有行为。测量有两个目的：一是找到真正影响整体性能的少数几个具体地方，二是建立基线，改完后再测，看看是否真的变快了。如果改动没有带来可测量的提升，就把它们撤掉，别留下没意义的复杂性。

当你已经通过分析确定了一段拖慢全局的代码后，最好的改善方式是做根本性改动，比如引入缓存或换用其他算法。如果没有这种机会，就要围绕关键路径重新设计代码。这应该是最后手段，但有时能带来很大不同。方法是先问自己，在最常见情况下完成任务需要的最少代码量是多少。忽略现有结构，想象你只写一段理想代码，只处理正常情况，把所有特殊情况都排除在外。然后再寻找新设计，让它尽量接近这段理想代码，同时保持整洁结构。你可以应用前面章节的设计思想，但要尽量保留理想代码的完整性。过程中最重要的一件事是从关键路径里移除特殊情况。代码慢往往是因为要处理各种不同情况，每个特殊情况都会在关键路径上增加条件判断或方法调用。重新设计时，尽量减少必须检查的特殊情况，最好开头只有一个 if 语句就能排除所有特殊情况，正常路径之后就不再需要额外测试。

RAMCloud 的 Buffer 类就是围绕关键路径优化的例子。Buffer 用来管理可变长度的内存数组，比如远程过程调用的消息。它允许底层存储分成多个不连续的块，从而减少内存复制和动态分配开销。Buffer 最常见的操作是用内部块追加少量数据。最初的实现里，关键路径要跨三个方法，检查六七个条件，层级又浅又重复。后来他们把设计完全围绕这条路径重构，引入 availableAppendBytes 变量，一次测试就把三种特殊情况全排除掉。新代码不仅快了一倍，类本身还小了百分之二十。书里有一张图对比了前后代码，你能看到新版本的路径干净得多。

本章最重要的经验是，简洁的设计和高性能是可以兼容的。重写 Buffer 类让性能提升两倍，同时简化了设计并减少了代码量。复杂的代码通常因为执行无关或冗余工作而变慢，而干净简单的代码正好去掉了这些多余部分。带走今天的核心观点：先用对性能的基本认知做自然高效的设计，遇到瓶颈再通过测量和关键路径简化来优化。下一集我们继续聊软件设计里另一个重要主题，敬请期待。
