# 第 11 集：设计两次

大家好，欢迎收听《软件设计的哲学》。今天我们来聊一个很多人容易忽略却非常关键的原则：设计两次。 [pause]

软件设计本来就难，你第一次想到的方案，很少能直接成为最好的方案。作者建议，对每一个重要的设计决策，都至少考虑两个不同的选项，这样最终的结果往往会好很多。为什么呢？因为第一次的想法通常只反映了你最熟悉的思路，而把几种方案放在一起对比，才能看出各自的优缺点。

拿管理图形界面文本编辑器里文件内容的类来说。第一次你可能会想到面向行的接口，只提供插入、修改、删除整行的操作。或者想到面向字符的接口，每次只处理单个字符的插入和删除。第三种可能是面向字符串的接口，能操作任意范围的字符，哪怕跨越多行。你不需要把每种方案的所有细节都写出来，只要把最重要的几个方法勾勒出来就行。关键是要让这些方案之间有明显差异，这样你才能真正学到东西。即使你觉得只有一种做法合理，也要硬着头皮想出第二种，哪怕它看起来很糟糕。把它的缺点和其他方案的优点放在一起比较，往往能带来意外的启发。

比较完之后，再逐一列出每个方案的优缺点。最重要的是看它对上层软件是否容易使用。在文本类的例子中，面向行和面向字符的接口都会让上层代码做额外工作：面向行的需要上层在剪切粘贴时拆分合并行，面向字符的则需要循环调用来处理多字符操作。另外还要考虑接口是否更通用、实现是否更高效。面向字符的方式因为每个字符都要单独调用，性能上通常会差不少。通过这样的对比，你会更清楚哪种方案真正合适。最好的结果甚至可能是把几种方案的优点融合成一个新设计，这个新设计往往比任何一个原始版本都更强。

当所有备选方案都不太理想时，就该把它们暴露出的问题当作信号，去寻找新的方案。比如只考虑面向行和面向字符两种方法时，你会发现两者都有一个共同的尴尬：都需要上层软件额外处理文本操作。这就是一个危险信号，说明文本类应该自己承担所有文本操作才对。由此你会想到，接口需要更贴近上层实际发生的操作，也就是面向范围的文本 API，这样才能彻底消除那些多余的工作。

这个“设计两次”的思路可以应用在不同层面。设计模块接口时可以用一次，设计具体实现时还可以再用一次。比如文本类的实现，你可以考虑基于行的链表、固定大小的字符块，或者间隙缓冲区。不同层级的目标也不同：接口设计最看重易用性，实现设计则更强调简单和性能。即使是系统级的用户界面特性选择，或者把系统拆成主要模块时，比较几种方案都能帮你找到更好的路径。

很多人担心这样做会多花很多时间，其实不然。对于一个类这样的小模块，你可能只需要一两个小时就能把备选方案想清楚。相比后面实现要花的几天甚至几周，这点时间几乎可以忽略。而且一开始多花的这点功夫，通常能换来明显更好的设计，整体收益是正的。 [pause]

作者特别提到，那些特别聪明的人反而更容易抗拒这个原则。因为他们从小到大，第一个想法往往就够用，不需要再想第二种、第三种。可当他们面对越来越复杂的系统时，第一次想法就不再足够了。坚持只做第一个方案，反而会限制他们发挥真正的潜力。真正聪明的做法，是承认问题本身很难，所以值得多花时间认真思考几种可能性。 [pause]

设计两次不仅能改善当下的设计，还能提升你整体的设计能力。反复比较不同方案的过程，会让你越来越清楚什么因素让设计变好、什么因素让设计变差。下次再遇到问题，你就能更快排除糟糕的选项，直接朝真正优秀的方案靠近。

带走今天这一集的核心：对每个重要设计，至少认真考虑两个差异明显的方案，再通过优缺点对比和问题驱动来优化。下一集，我们将讨论如何在更大尺度上应用这些设计思路。
