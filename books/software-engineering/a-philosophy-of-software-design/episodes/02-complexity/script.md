# 第 2 集：复杂性的本质——变更放大、认知负荷与未知的未知

大家好，欢迎回到《软件设计的哲学》有声博客。今天是第二章：复杂性的本质。先问一句：你怎么判断一个系统「太复杂了」？是代码行数多？功能多？还是改起来总踩坑？[pause]

作者给了一个很实用的定义：复杂性，是指那些让软件系统难以理解和修改的任何事物。可能是看不懂一段代码怎么工作，可能是小改进也要花大力气，可能是不清楚该改哪里，也可能是修一个缺陷却容易引出新问题。难理解和难修改，就是复杂；容易理解和修改，就是简单。也可以从成本收益看：复杂系统里，小改进要大量工作；简单系统里，更少精力就能换来更大改进。

注意：复杂性是开发者在特定时间、为特定目标所经历的感受，不一定等于系统整体大小或功能多少。一个功能很炫的大型系统，如果用起来顺手，按本书的定义未必算复杂；反过来，小而功能不花哨的系统，也可能非常复杂。复杂度还取决于最常见的活动。若某处极复杂却几乎没人碰，对整体影响就不大。粗略地说，总体复杂性 C，是各部分复杂性 cp 乘以在该部分上花的时间 tp，再加权求和。把复杂性隔离到几乎看不见的地方，几乎和彻底消灭它一样好。[pause]

读者往往比作者更容易感到复杂。你写的代码对自己很简单，别人却觉得复杂，那它就是复杂的。这时值得问问对方为什么难，从视角落差里学到东西。你的工作不只是写出自己能用的代码，还要让别人也能轻松用。

复杂性有三种典型症状。第一，变更放大：看似简单的改动，要在很多地方改代码。书里用网站横幅背景色举例——早期每个页面各自写死颜色，改一次色几乎要改遍所有页；现代做法是在中心位置指定一次，各页引用共享值，一改全站变。图意就是：分散重复 vs 中心变量。[pause]

第二，认知负荷：完成任务需要掌握多少知识。负荷高，就要花更多时间学，也更容易漏掉关键信息而出错。比如 C 里某个函数分配内存、返回指针，却假定调用者负责释放——调用者多记一件事，忘了就泄漏。若能重组系统，让分配的模块也负责释放，认知负荷就下降。API 方法特别多、全局变量、不一致、模块间依赖，都会推高认知负荷。别只用代码行数当复杂度尺子：有时框架「几行就能写应用」，但搞清那几行是什么极其困难。有时多写几行，反而更简单，因为负荷更低。

第三，也是最糟的：未知的未知。你不清楚为了完成任务必须改哪些代码，也不清楚必须知道哪些信息。还是横幅例子：中心变量控制背景色，看起来好改；但有些页用更深的强调色，且写死在各页里。背景一变，强调色也得跟着变。开发者可能根本不知道这回事；就算知道，也不清楚哪些页用了强调色，可能要搜遍全站。变更放大很烦人，但只要知道改哪里，改完系统还能工作；高认知负荷提高成本，但若清楚该读什么，仍可能改对。未知的未知则是：你不知道自己不知道，甚至不知道有没有问题，直到改出缺陷才发现。唯一「确定」的办法是读完每一行代码——对稍大的系统都不现实。良好设计最重要的目标之一，就是让系统容易理解，对抗高认知负荷和未知的未知。[pause]

原因呢？两件事：依赖性和模糊性。无法孤立地理解和修改某段代码时，就存在依赖——它和别的代码有关，改它就要考虑或改别处。页面间共享背景色、网络协议收发两端、方法签名与调用方，都是依赖。依赖无法也不应完全消除：每写一个新类，就会围绕其 API 引入依赖。目标是减少数量，并让依赖尽量简单、明显。网站例子里，旧做法让所有页互相依赖；新做法用中心 API 取背景色，消掉页与页之间的隐式依赖，换成更明显、更好管理的 API 依赖——改名甚至能靠编译器帮忙抓漏。

模糊性则是：重要信息不明显。变量名过于笼统、文档没写单位、依赖的存在本身不显眼、同一名字用于两个目的造成不一致……都是模糊。文档不足常是来源，但模糊也是设计问题：设计简洁明了，所需文档就更少；需要海量文档，往往是设计不对的危险信号。最好的办法仍是简化设计。

依赖性和模糊性一起，撑起三种症状：依赖带来变更放大和高认知负荷；模糊制造未知的未知，也抬高认知负荷。压低依赖与模糊，就能压低复杂性。[pause]

最后一点关键：复杂性是增量产生的。不是一次灾难，而是成千上万个小依赖、小模糊慢慢堆出来。单个问题本身往往无不痛痒；但每个开发者都觉得「这一点点没关系」，复杂性就会迅速累积。堆起来之后又很难消，因为修掉一两个几乎感觉不到。所以要有下一章会讲的「零容忍」理念。

小结带走三句话：复杂性等于难理解、难修改；盯三种症状，尤其警惕未知的未知；根子是依赖与模糊，而且它总是一点点长出来的。下一集：能工作的代码还不够——战术式编程 vs 战略式编程。我们下集见。
