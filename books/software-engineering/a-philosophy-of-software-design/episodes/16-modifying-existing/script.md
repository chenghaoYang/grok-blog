# 第 16 集：修改现有的代码

大家好，欢迎收听《软件设计的哲学》有声博客。我是撰稿人，今天我们进入第十六章，讨论如何在修改现有代码时防止复杂性不断蔓延。大型系统从来不是一次设计完成的，而是通过一次次演化逐步成形，所以每一次修改都可能让设计变得更好，也可能让它慢慢失控。[pause]

很多开发者面对缺陷修复或新功能时，心里默认的做法是“实现这个需求，我能做的最小改动是什么”。这种心态看似谨慎，因为担心大改动会引入新问题，却恰恰落入了战术式编程的陷阱。每次最小改动都可能增加特殊情况、新的依赖关系或其他形式的复杂性。久而久之，系统设计就一点点变差，而这些问题会在后续每一次演化中继续累积。作者强调，当你修改代码时，必须采取战略式思考。理想情况下，当你完成这次更改后，系统的整体结构应该像一开始就考虑过这个需求一样，而不是临时打补丁。

要达到这个目标，就需要抵制快速解决问题的诱惑。相反，你应该先审视当前设计是否仍然是最优的。如果不是，就先重构系统，再实现所需功能。这样每次修改都在持续改善设计，而不是让它退化。这其实就是第三章提到的投资思维：多花一点时间重构和清理设计，会换来更整洁的系统，长远来看能加快后续开发速度，让你收回投入的精力。作者甚至指出，如果你没有让设计变得更好，那你其实很有可能正在让它变得更糟。

当然，现实中总会遇到冲突。比如重构需要三个月，而快速但不整洁的修复只需两小时；或者大规模重构会造成不兼容，影响其他团队。这时你可能不得不妥协。但作者建议我们问自己：考虑到目前的限制，这是否已经是我能做的最整洁工作？也许存在另一种方案，既接近理想设计，又能在几天内完成。或者你可以和老板协商，在当前截止日期之后再分配时间做清理。每个开发组织都应该把全部工作的一小部分固定用于重构和清理，从长远看这项投入一定是值得的。

修改代码时，注释很容易失效。作者给出的第一个实用方法是把注释放置在它描述的代码附近。方法接口注释最好直接写在实现文件的代码旁边，这样改动代码时注释就在眼前，开发者自然会看到并更新它。相比之下，把注释放在单独的头文件中，距离代码太远，修改时容易忽略。把实现注释拆开，放在每个阶段代码正上方，也比全部堆在方法开头更有效。作者举例说，如果一个方法分三个阶段，可以在方法顶部写一段概述策略的注释，然后把各阶段细节分别放在对应代码上方。这样注释与代码的距离越近，被正确维护的可能性就越大。

另一个常见错误是把改动细节只写进提交日志，而不是代码本身。作者指出，未来的开发者不会主动去翻日志，他们只会阅读代码。如果某个微妙问题的修复只记录在日志里，后人可能不小心撤销这个改动，重新引入缺陷。因此，凡是以后可能需要的信息，都应该直接写在代码中。提交日志可以保留副本，但最关键的内容必须放在代码里。

避免重复是保持注释更新的第二招。同一设计决策只记录一次，放在最明显的位置。比如某个变量的棘手行为影响多处使用，就只在变量声明旁的注释里说明，其他地方如果需要引用，可以用简短指向句指向这个中心位置。如果没有明显位置，可以创建一个 designNotes 文件，或者在现有位置中选一个最好的放进去。不要把被调用方法的内部逻辑写在调用处，也不要在程序里重复外部文档已经记录的内容，比如 HTTP 协议细节或用户手册里的命令说明，只需在代码中加一句引用即可。

提交前花几分钟检查所有变更，也能有效防止注释滞后，同时发现调试代码或未完成的 TODO 项。最后，作者提到更高层级的注释更容易维护，因为它们更抽象，不受代码细节小改动的影响，只有整体行为变化时才需要调整。

带走今天的关键：修改现有代码时，始终保持战略式思考，优先改善设计，同时把注释放在代码附近、避免重复、提交前检查一遍。下一集我们将讨论如何在大型系统中管理依赖关系，敬请期待。
