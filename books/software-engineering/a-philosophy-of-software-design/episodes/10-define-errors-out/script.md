# 第 10 集：通过定义来规避错误

各位听众大家好，欢迎来到《软件设计的哲学》有声博客。今天我们来聊聊异常处理这个让人头疼的话题。很多程序员都遇到过这样的场景：一段简单的文件读取代码，外面却裹着层层 try-catch 块，读起来比正常逻辑还长。异常处理为什么会让系统变得这么复杂？本章给出了一个核心思路：与其费力去处理异常，不如从定义上把异常消灭掉。[pause]

先说说异常为什么特别麻烦。作者把“异常”定义为任何会打断正常控制流的罕见情况，不管是用 throw 还是返回特殊值。调用方传错参数、底层 I/O 失败、网络丢包、甚至内部 bug，都可能触发异常。问题在于，异常处理代码天生就比正常路径难写。它会中断流程，系统状态可能已经不一致，程序员要么硬着头皮往前走，要么中止操作并向上报告，而这两种选择都容易引入新问题。重发丢包可能制造重复包，恢复冗余数据时又可能遇到次级异常。语言提供的 try-catch 语法又冗长笨拙，异常真正发生时还很难测试，所以很多灾难性故障其实都来自错误处理代码。

更糟糕的是，程序员常常无意中制造了太多不必要的异常。作者在设计 Tcl 时就犯过这个错：unset 命令在变量不存在时抛错，结果最常见的清理场景反而要用 catch 吞掉错误。把问题甩给调用者，看似灵活，其实只是把复杂性传递了出去。类暴露的异常越多，它的接口就越复杂，也就越浅。

那该怎么减少必须处理异常的地方呢？最彻底的办法就是“通过定义来规避错误”。把操作的语义重新定义一下，让正常行为覆盖所有情况，就不用再报告异常了。还是拿 Tcl 的 unset 举例：与其说“删除变量”，不如改成“确保变量不再存在”。这样变量本来就不存在时，命令直接返回就行，没有错误需要处理。

文件删除是另一个好例子。Windows 不允许删除已打开的文件，用户常常要杀进程或重启才能清理。Unix 的做法更聪明：删除正在使用的文件时，系统只是标记删除并立即返回成功，文件名从目录里消失，但已打开文件的进程还能继续读写，直到最后一个句柄关闭才真正释放数据。这样既避免了删除操作报错，也避免了让正在使用的进程收到异常。

Java 的 substring 方法也一样。原来的定义是索引越界就抛 IndexOutOfBoundsException，用起来很麻烦。作者建议改成“返回范围内存在的字符（如果有）”，这样索引超出范围时自动取交集，不再抛异常，方法反而更深、更好用。Python 的列表切片就是这么做的。

当然，不是所有异常都能直接定义掉。作者还介绍了另外三种减少异常处理点的方法。第一种是异常屏蔽：在底层把问题解决掉，上层完全感知不到。比如 TCP 通过重传屏蔽丢包，NFS 在服务器宕机时让客户端挂起而不是抛异常给应用。屏蔽虽然会让操作暂时停顿，但比到处写错误处理代码要干净。

第二种是异常聚合。书里有一张图对比了两种写法：一种是每个 getParameter 调用都包一层 try-catch，另一种是让异常冒泡到顶层调度器，用一个统一的 handler 生成错误响应。这样重复代码消失了，而且新方法只要抛出同类异常就能自动复用这个 handler。

第三种是干脆让程序崩溃。对于内存不足、磁盘硬错误、内部数据结构损坏这类情况，恢复往往得不偿失。作者建议写一个 ckalloc 包装 malloc，失败时直接打印信息并中止，而不是让每个调用者检查返回值。崩溃虽然听起来粗暴，但在这些罕见且难以恢复的错误上，反而能降低整体复杂性。

当然，屏蔽和定义规避也不能过头。如果调用者真的需要知道网络断了，那模块就必须把异常暴露出来，否则上层无法构建健壮的应用。关键在于判断哪些情况重要，哪些可以隐藏。

带走今天的关键点：减少异常处理复杂性的最好办法，是重新定义操作语义来消灭异常，其次是底层屏蔽、聚合处理，以及在必要时让程序崩溃。这些做法都能显著降低系统中异常处理代码的数量。下一集，我们将讨论如何通过“通用机制”进一步简化设计，敬请期待。
