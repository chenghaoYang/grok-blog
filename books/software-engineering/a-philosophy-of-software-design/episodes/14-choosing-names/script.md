# 第 14 集：选取名称

大家好，欢迎收听《软件设计的哲学》。今天我们来聊聊软件设计里最容易被忽略，却又最容易出问题的一件事——给变量、方法和其他实体起名字。 [pause]

先讲一个真实的故事。二十世纪八十年代末，我参与开发一个叫 Sprite 的分布式操作系统。系统偶尔会莫名其妙地把文件里的数据块清零，用户根本没动过文件，却丢失了数据。几个研究生找了很久都没找到根源，最后放弃了。我却觉得不能放过这个缺陷，花了整整六个月才抓到它。问题其实很简单：文件系统里有一个变量叫 block，它在不同地方分别代表磁盘上的物理块号和文件里的逻辑块号。有一处代码把逻辑块号传到了需要物理块号的地方，结果就把无关的磁盘块写成了全零。 [pause]

为什么这么多人读过这段代码都没发现问题？因为变量名叫 block，大家下意识就以为它就是物理块号。直到后来我强迫自己去追这个变量的来源，才绕过这个思维障碍。如果当时用了 fileBlock 和 diskBlock 这样的名字，错误很可能根本不会发生。甚至更好的做法是给它们定义不同类型，让编译器直接帮我们拦住这种混用。

这个故事说明，名字选得不好，不只是阅读起来别扭，它会直接制造缺陷。软件里有成千上万个变量，每个都选一个平庸的名字，累积起来就会让整个系统变得复杂而脆弱。

那怎么才能选出好名字呢？核心目标是让读者看到名字就能在脑子里立刻勾勒出这个实体的本质。名字其实是一种抽象，它要突出最重要的特征，同时忽略次要细节。 [pause]

第一个关键属性是精确。很多名字太宽泛，像 count、status、result 这样的词，几乎什么都能指。举个例子，有个方法叫 getCount，注释说返回管理的 indexlet 总数。可读者看到调用时，还是得去翻文档才能知道它到底在数什么。如果改成 numActiveIndexlets，大多数人一眼就能猜到。另一个学生项目里，用 x 和 y 表示字符在文件里的位置，结果这两个字母也可能被理解成屏幕像素坐标。改成 charIndex 和 lineIndex 后，代码立刻清晰多了。

再看布尔变量。有人用 blinkStatus 表示光标是否可见，status 这个词对布尔值来说太模糊了。改成 cursorVisible 后，读者不仅知道它在描述可见性，还能立刻理解 true 的含义——光标正显示着。布尔变量的名字最好直接是个谓词，这样真假值就不用猜了。

名字也可能太具体。有个删除文本的方法，参数叫 selection，结果暗示只能删当前选中的内容。可实际上它能删任意范围。把参数改成 range 反而更准确，因为它没有多余的假设。

当你发现很难给某个变量起一个既精确又简短的名字时，这往往是个危险信号。它可能意味着这个变量本身职责不清。也许你正试图用一个变量同时代表好几件事，这时候拆成多个变量，反而能让每个名字都变得简单。

第二个关键属性是一致性。在同一个系统里，同样的概念应该反复使用同一个名字。比如文件系统里所有表示文件内块索引的地方，都固定用 fileBlock。读者一旦在一个地方学会了这个名字，在别处看到它就能立刻复用理解。反过来，如果同一个名字在不同地方行为不一致，就像前面 block 的例子，就会制造误解。 [pause]

一致性还有个小技巧：当需要多个同类变量时，用前缀区分。比如复制文件时，需要源块和目标块，就写 srcFileBlock 和 dstFileBlock。循环变量也一样，永远让最外层循环用 i，内层用 j，读者看到就能立刻知道层级关系。

名字里每个词都要有信息量。像 fileObject 里的 Object、filePtr 里的 Ptr，往往是多余的。现代 IDE 能直接显示类型，再把类型信息塞进名字只会增加阅读负担。同样，一个 File 类的实例变量叫 fileBlock，也不如直接叫 block，因为上下文已经清楚它属于 File 类了。

当然，也有人持不同看法。Go 语言社区有人主张名字越短越好，甚至用单字母。他们举例说，短名字不会遮蔽代码逻辑。但我个人读下来，count 总比 n 更能让人一眼看出意图。除非整个系统都严格约定 n 只表示计数，否则短名字更容易带来歧义。 [pause]

最后想说，选好名字是一项值得的投资。你多花几分钟想一个精确、一致的名字，以后阅读和维护代码时就能省下大量时间，也能减少缺陷。刚开始可能会觉得费力，但练习多了，命名会越来越自然。最终你几乎不用额外思考，就能写出清晰的代码。

带走今天的关键：名字要精确、一致，避免多余词，并且把一致性贯穿整个系统。下一集我们继续聊软件设计里的另一个重要话题，敬请期待。
