# 第 1 集：介绍——软件最大的限制是理解力

大家好，欢迎回到《软件设计的哲学》有声博客。上一集我们听了作者为什么写这本书；今天进入第一章：介绍。先用一个钩子抓住你：写软件几乎不受物理定律约束，你可以造出现实里不存在的虚拟世界。编程也不要求芭蕾或篮球那种高身体技能。你需要的是有创造力的头脑，以及组织思想的能力。如果你能把一个系统具象化，就能在程序里实现它。那真正限制我们的，到底是什么？[pause]

答案是：我们理解自己所造系统的能力。随着程序演进、功能加入，它变得越来越复杂，组件之间出现微妙依赖。复杂性不断累积，程序员在修改时要把所有相关因素牢记在心，变得越来越难。这会减慢开发，导致缺陷，再进一步拖慢开发、抬高成本。在任何程序的生命周期里，复杂性都会不可避免地增加。程序越大、工作的人越多，管理复杂性就越困难。

好的开发工具能帮忙，过去几十年也造出了许多出色工具。但仅凭工具，能做的事仍有限。若想简化写软件的过程，用更低成本构建更强大的系统，就必须找到简化软件本身的方法。尽管我们尽了最大努力，复杂性仍会随时间增加；但更简单的设计，能让我们在复杂性取得压倒性优势之前，构建出更大、功能也更强的系统。[pause]

有两种解决复杂性的通用方法，本书都会讨论。第一种：通过让代码更简单、更易理解来消除复杂性。例如，消除特殊情况，或以一致的方式使用标识符。第二种：封装复杂性，让程序员在系统上工作时，不必立刻暴露在全部复杂性面前。这叫模块化设计。系统被分成模块，比如面向对象语言中的类；模块彼此相对独立、低耦合，从而可以在一个模块上工作，而不必了解其他模块的细节。

因为软件延展性很好，软件设计是贯穿系统整个生命周期的连续过程。这与建筑物、船舶、桥梁这类物理系统的设计不同。但软件设计并非总是被这样看待。早期设计往往集中在项目开头，像其他工程学科一样。极端就是瀑布模型：把项目分成需求定义、设计、编码、测试、维护等离散阶段；每阶段在下一阶段开始前完成，有时各阶段由不同的人负责。设计阶段一次性设计整个系统，结束时冻结设计，后续只是充实和实现。[pause]

不幸的是，瀑布很少适用于软件。软件本质上比物理系统更复杂。在构建任何东西之前，几乎不可能充分具象化大型软件系统的设计，以了解其所有含义。初始设计会有许多问题；实现到一定程度之前，问题不会变得明显。而瀑布此时又难适应重大设计变更——设计师可能已转到别的项目——于是开发者尝试在不改整体设计的前提下解决问题，导致复杂性爆炸式增长。

由于这些问题，当今多数软件项目使用增量方法，比如敏捷：初始设计只着眼于整体功能的一小部分。这一小部分被设计、实现、评估；发现并纠正原始设计中的问题后，再设计、实现、评估更多功能。每次迭代暴露现有设计的问题，在设计下一组功能之前就解决掉。系统仍小时就修掉初始设计的问题；较新的功能受益于较早功能实现中获得的经验，问题也会较少。增量方法适用于软件，正因为软件够延展，实施过程中可以做重大设计变更；而对物理系统，比如施工中改支撑桥梁的塔架数量，就不切实际。[pause]

增量开发意味着软件设计永远不会完成。设计在系统整个生命周期中不断发生：开发者应始终思考设计问题。增量也意味着不断重新设计。系统或组件的初始设计几乎从来不是最好的；随着经验累积，不可避免地会产生更好的做事方式。作为软件开发者，你应始终寻找机会改进正在开发的系统的设计，并计划把部分时间花在设计改进上。

如果开发者应始终考虑设计问题，而降低复杂性又是软件设计中最重要的要素，那么开发者应始终考虑复杂性。这本书，就是关于如何用复杂性来指导软件设计的整个生命周期。

本书有两个总体目标。第一：描述软件复杂性的本质——「复杂性」是什么意思、为什么重要、程序有不必要的复杂性时如何识别。第二也更有挑战：介绍可在开发过程中使用的技术，以最大程度减少复杂性。没有简单方法能保证出色设计。作者提出的是与哲学相关的更高层级概念，例如「类应该是深的」或「通过定义来规避错误」。这些概念可能不会立即确定最佳设计，但你可以用它们比较备选方案，并引导你探索设计空间。[pause]

怎么用这本书最好？与代码审查结合。读别人的代码时，考虑它是否符合这里讨论的概念，以及它与代码复杂性的关系。在别人的代码里，往往比在自己的代码里更容易看到设计问题。你可以用书里描述的危险信号来发现问题并提出改进。审查也会让你接触新设计方法和编程技术。

改善设计技能最好的方法之一，是学会识别危险信号：它们表明一段代码可能比需要的更复杂。编码时看到危险信号，就停下来寻找可消除问题的替代设计。刚开始你可能要尝试几种替代方案才能消掉危险信号。不要轻易放弃：解决问题之前尝试的替代方法越多，你学到的就越多。随着时间流逝，你会发现代码中的危险信号越来越少，设计越来越清晰。

应用这些思想时，务必要节制和谨慎。每条规则都有例外，每条原则都有其局限。若把任何设计创意发挥到极致，都可能陷入困境。精美设计反映相互竞争的思想与方法之间的平衡。书中有些章节标题为「做过头了」，专门描述如何识别自己是否把事情做得过头了。例子多用 Java 或 C++，讨论多针对面向对象语言中的类设计；但思想也适用于其他领域——几乎所有与方法有关的想法，也可用于没有面向对象特性的语言中的函数，例如 C；设计思想也适用于类之外的模块，比如子系统或网络服务。

小结带走什么：软件最大的限制是理解力；用消除与封装两条路径对抗复杂性；把设计当作贯穿生命周期的增量过程，并用危险信号训练你的眼睛。下一集我们进入第二章，正面定义复杂性：三种症状、两大原因，以及为什么复杂性总是一点点长出来的。我们下集见。
