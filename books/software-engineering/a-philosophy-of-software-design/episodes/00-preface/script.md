# 第 0 集：前言——为什么需要一本讲软件设计的书

大家好，欢迎来到《软件设计的哲学》有声博客。我是你的讲解员。这一系列会带你走进 John Ousterhout 的经典小书第二版中译。今天先从前言说起：作者为什么要写这本书？[pause]

八十多年来，人们一直在为计算机写程序。奇怪的是：关于「怎样设计程序」「什么叫好的程序」，讨论却出奇地少。敏捷流程、调试器、版本控制、测试覆盖工具——这些开发过程与工具，讨论已经很多。面向对象、函数式、设计模式、算法——这些编程技术，分析也很广泛。它们都有价值。但软件设计的核心问题，很大程度上还没被真正碰过。作者提到，David Parnas 那篇关于「把系统分解成模块的标准」的经典论文发表于一九七一年，此后四十多年里，软件设计的技术水平似乎并没有明显超过它。

计算机科学里最基本的问题，其实是「问题分解」：怎样把一个复杂问题拆成可以独立解决的部分。这是程序员每天都要面对的首要设计任务。可作者说，除了这本书里描述的工作之外，他几乎没在任何大学里找到一门以问题分解为中心的课。我们教 for 循环，教面向对象，却很少系统讲授软件设计。[pause]

更让人沮丧的是：不同程序员在产出质量和效率上差距巨大，我们却很少尝试去弄清「最好的程序员到底强在哪里」，更少把这些技能搬进课堂。作者和几位他认为优秀的程序员聊过，多数人很难说清赋予自己优势的具体技术。许多人觉得软件设计技能是天生的，教不了。但不少科学证据表明，很多领域的杰出表现，更多地与高质量的实践有关，而不是先天能力——比如 Geoff Colvin 那本讨论练习与卓越的书所指出的方向。

这些问题让作者困惑、也沮丧了很多年。他想知道：软件设计能不能教？设计技巧是不是区分优秀与普通程序员的关键？最终他决定：回答这些问题的唯一办法，是亲自去开一门软件设计课。结果就是斯坦福大学的 CS 190。课上他提出一套设计原则，让学生用一系列项目去学习和实践；授课方式很像传统英语写作课：写草稿、收反馈、再改稿。学生从头开发大量软件，再进行大量代码审查以识别设计问题，然后修改项目。这样，学生能看到：应用设计原则之后，代码怎样变好。[pause]

原则本身偏抽象，像哲学概念——比如「通过定义来规避错误」——学生很难单靠抽象理解。通过写代码、犯错、再看到错误与修正如何对应到原则，学得最好。

你可能会问：凭什么作者觉得自己知道软件设计的答案？他坦言：他并不知道全部答案。他学编程时没有设计课，也没有导师系统教原则；那时代码审查还不常见。他对设计的想法，来自写代码和读代码的个人经验。职业生涯中大约写过二十五万行代码，用过多种语言；曾在从零创建三个操作系统的团队里工作，还做过多个文件与存储系统、调试器与构建系统、脚本语言，以及文本、图形、演示和集成电路的交互式编辑器。一路上他亲历大型系统的问题，试过各种设计技术；也读过大量别人的代码，接触到好坏不一的方法。从这些经验里，他试图抽出通用线索：该避免的错误，该使用的技巧。书中每个问题，都是他亲身经历过的；每条建议，也是他在自己编码中成功用过的。

他不希望这本书成为软件设计的「定论」。他肯定漏了有价值的技术，长远看有些建议也可能变成坏主意。但他希望开启对话：把书中想法与你自己的经验比较，看这些方法是否真的降低了软件复杂性。这是呈现个人观点的书，有人会不同意——若不同意，试着弄清原因在哪。总体目标永远是降低复杂性，比任何一条具体原则或想法都更重要。如果你试用某个想法，发现它并没有降低复杂性，那就不必继续用它。[pause]

好，前言先到这里。下一集我们进入第一章：为什么软件设计必须围绕「复杂性」展开，以及这本书该怎么用。我们下集见。
