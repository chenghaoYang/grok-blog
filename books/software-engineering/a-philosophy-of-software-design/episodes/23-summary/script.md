# 第 23 集：总结

大家好，欢迎收听《软件设计的哲学》有声博客。今天是系列的最后一集，我们来把全书最重要的设计原则和危险信号串起来回顾一遍。[pause] 很多时候我们写代码时，总觉得先让功能跑起来再说，结果小问题一点点堆积，最后整个系统变得难以维护。书里反复强调，复杂性是增量产生的，所以必须从一开始就处理那些看起来不起眼的小事。

核心在于，仅仅让代码能工作远远不够。我们需要持续做小额投资来改善设计，而不是等到大重构才动手。模块应该做深，也就是接口要远比实现简单得多。接口设计的核心是让最常见的用法最简单，而不是把所有可能性都暴露出来。让模块的接口保持简单，比让它的实现简单更重要，因为接口是别人每天要面对的。

通用模块往往更深，所以要把通用代码和专用代码分开，避免混在一起。不同层级要用不同抽象，下沉复杂性，让上层保持干净。通过定义来规避错误，而不是到处加检查。设计时最好多想两遍方案，注释只写那些代码里不容易看出来的东西。整个系统要为阅读而设计，而不是为编写方便。开发的增量应该是抽象的提升，而不是功能的堆砌。最后，要区分重要和不重要的事情，并把重点突出出来。[pause]

这些原则如果没做好，就会出现各种危险信号。浅模块的接口和实现差不多大，信息泄露让设计决策散落在多个地方，时间分解让代码结构跟着执行顺序走而不是信息隐藏。过度暴露会强迫调用者了解很少用的功能，透传方法几乎什么都不做只是把参数往下扔。重复代码、通用专用混合、连体方法这些，都会让系统越来越难理解。注释如果只是重复代码，或者把实现细节污染到接口里，也会增加阅读负担。变量或方法的名字模糊、难以取名、描述起来很长，这些都是设计本身不够清晰的信号。最终代码如果让人难以理解，就说明抽象出了问题。[pause]

书里把这些危险信号一一列出，就是提醒我们，一旦出现这些症状，就该停下来审视设计了。举个例子，当你发现两个方法互相依赖到必须看懂一个才能懂另一个时，这就是连体方法的典型表现，需要重新划分边界。

带走这些原则：把复杂性控制在源头，让模块接口保持简洁而深邃，持续小步改进，并警惕那些浅模块、信息泄露和重复等信号。本系列到此结束，感谢大家一路收听，希望这些内容能帮到你的日常设计。
