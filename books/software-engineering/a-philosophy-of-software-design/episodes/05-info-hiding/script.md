# 第5集：第5章 信息隐藏和信息泄露

大家好，欢迎收听《软件设计的哲学》。今天我们来聊一个让很多程序员头疼的问题：为什么你的模块总是改一点就牵连一大片？[pause] 答案往往藏在信息隐藏做得不够彻底上。

信息隐藏的核心思想很简单，每个模块都该把一些设计决策和实现细节藏起来，只通过接口暴露必要的功能。这些被隐藏的知识可能包括B树怎么存储数据、TCP协议怎么处理拥塞、或者JSON文档怎么解析。隐藏的内容既可以是底层细节，比如页面大小，也可以是较高层的假设，比如大多数文件都很小。好处有两个：第一，接口变得更简单干净，使用者不用操心扇出平衡或者页面大小这些细节，认知负担大大降低；第二，系统更容易扩展，因为改动只影响一个模块，其他地方不受波及。反过来，如果一个设计决策同时出现在多个模块里，那就是信息泄露。哪怕这些知识没直接写在接口上，只要两个类都懂同一个文件格式，改格式时就得两边都改，这种后门泄露比接口泄露还隐蔽，也更难发现。

设计时最容易掉进的坑叫时间顺序分解。很多人写代码时按操作顺序拆类，比如先读文件、再改内容、最后写文件，结果读和写两个类都得懂文件格式，导致知识重复。正确的做法是把同一块知识集中到一个模块里，而不是按执行顺序拆分。记住，模块结构应该围绕“需要哪些知识”来组织，而不是“先做什么后做什么”。顺序当然重要，但除非不同阶段用到的知识完全不同，否则不该让执行顺序决定类的划分。

书里举了HTTP服务器的例子。学生项目常犯的错是把接收请求拆成两个浅类：一个读字符串，一个解析字符串。因为不解析就不知道Content-Length，所以两个类都得重复掌握请求结构，调用者还得按固定顺序调用方法。更好的办法是合并成一个类，同时处理读取和解析，把所有格式知识藏在里面，只给调用者一个简单方法。另一个常见问题是参数接口太浅，直接返回内部Map，暴露了存储方式，还让调用者多写好几行代码。改进后的接口提供getParameter和getIntParameter，直接返回解码后的值，把URL编码和存储细节全藏起来。

同样在响应处理上，很多项目要求调用者手动指定协议版本，其实这个版本可以从请求里自动推导出来。好的设计应该提供默认值，让常见场景零配置就行，只有极少数情况才需要覆盖。默认值既简化了接口，又隐藏了部分信息，使用者甚至不用知道它的存在。HTTP响应里的日期头也该自动生成，而不是每次都让调用者操心。

当然，信息隐藏也不能过头。如果模块外部真的需要某些配置来调优性能，就该把它们暴露出来，但目标始终是尽量减少外部必须知道的东西。类内部也可以做信息隐藏，比如把私有方法设计成各自封装一块知识，减少实例变量的使用范围。

带走的关键点是：深模块靠信息隐藏来实现，隐藏得越多，接口越简单、功能越集中。避免时间顺序分解，把知识而不是执行顺序作为拆分依据。下一集我们继续看创建深模块的其他实用技巧。
