# 第 7 集：不同的层级，不同的抽象

大家好，欢迎收听《软件设计的哲学》。今天我们聊聊系统里最容易被忽略却又最要命的一件事：不同层级该用不同抽象。[pause]

想象一下，你在文件系统里读一个文件。最上层你看到的是可变长度的字节数组，想读哪段就读哪段；再往下是固定大小的磁盘块缓存，调用者可以放心地认为常用块会留在内存里，访问速度很快；最底层则是设备驱动，在内存和硬盘之间搬数据。每一层都在做上一层不想管的事，抽象完全不一样。这就是设计良好的样子。再比如 TCP 网络协议，最顶层让你感觉像在两台机器之间可靠地传送一整条字节流，而它下面那层却只管尽最大努力发固定大小的数据包，丢包、乱序全不管。层与层之间抽象差异明显，系统才不容易出问题。

反过来，如果相邻两层抽象几乎一模一样，那多半出问题了。问题最常见的表现，就是透传方法。一个类里十几个公有方法，十三个只是把参数原封不动扔给另一个类去做。这样的方法让类接口变复杂，却没增加任何新功能，还把两个类的命运绑在一起。签名一改，上层全得跟着改。书里举了一个学生做的文本编辑器。TextDocument 类几乎全是透传，调用 TextArea 的同名方法，比如 getLastTypedCharacter、getCursorOffset、insertString 等。十五个公有方法里居然有十三个是这样。三个类职责重叠，谁该管插入，谁该管监听，全乱了。

为什么会这样呢？因为透传方法除了把调用转发出去，几乎什么都不做。它让上层类显得更浅，却没有真正封装任何东西。调用者本该直接面对实现功能的那个类，结果却多绕了一层。重构的时候，作者建议几种方式：可以把下层类直接暴露给调用者，从上层彻底移除对应职责；也可以在两个类之间重新分配功能，让每个方法真正属于负责它的类；如果实在分不开，就干脆把两个类合并。学生最终把三个类缩成两个，每个类的边界就清晰了。书里还有一张图，画了四种情况，从透传方法堆积到最终消除的过程，看起来一目了然。

当然，并不是所有签名重复都坏。分发器就是一个正面例子。Web 服务器收到 HTTP 请求后，用一个分发器根据 URL 决定该调用哪个处理方法。有些 URL 直接返回磁盘文件，有些则交给 PHP 或 JavaScript 程序执行。分发过程可能很复杂，但它真正做了选择和路由的工作，提供了新价值。只要每个方法都贡献了独特功能，重复接口就没问题。另一个例子是操作系统里的磁盘驱动程序，不同驱动实现不同磁盘，但接口完全一样，使用过一个就容易用其他，认知负担反而降低。

装饰器模式则很容易把坏事做大。它鼓励你为每个小功能再包一层，结果到处都是透传方法。Java 的 BufferedInputStream 就是典型，给 InputStream 加缓冲，却复制了大量相同 API。窗口系统里的 ScrollableWindow 也是如此，在 Window 基础上加滚动条，却让类变浅。作者建议先问几个问题：新功能能不能直接并进基础类？是不是只针对特定场景？能不能和已有装饰器合并？或者干脆做成独立类，不去包装？包装器只有在必须适配外部不可改接口时才值得考虑，否则很容易导致浅类泛滥。

另一个容易被忽视的点是，类的接口和它的内部实现也该有不同抽象。文本编辑器项目里，有些团队用“行”来存文本，同时也把 getLine、putLine 暴露给上层。结果用户界面在行中间插字、跨行删除时，就得到处拆行接行，代码又臭又长。如果接口改成面向字符的 insert 和 delete，内部依然按行存，但上层代码就简单多了。抽象的差异，正是这个类存在的价值。

跨层传递变量也是同类问题。命令行里的证书参数，要一路透传给最底层的 socket 调用，中间所有方法签名都得改。更好的做法是把这些系统级信息集中放到一个 Context 对象里。每个主要对象保存 Context 的引用，构造函数里传一次就够。新加配置项时，只改 Context，其它代码基本不动。书里另一张图展示了四种处理方式，从透传变量到使用 Context 的对比。Context 不是完美方案，但它比满天飞的透传变量和全局变量要好管得多。[pause]

带走今天的关键：相邻层级如果抽象重复，就说明这一层没提供足够价值，反而增加了理解负担。无论是透传方法、装饰器，还是透传变量，都指向同一个信号——该重新切分职责了。
