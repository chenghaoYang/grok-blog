# 第19集：软件发展趋势

大家好，欢迎收听《软件设计的哲学》。今天我们来聊聊过去几十年软件开发里那些热门的趋势和模式，看看它们到底是帮我们对抗复杂性，还是反而让事情更麻烦。[pause]

先从面向对象编程说起。它带来了类、继承、私有方法这些机制，用得好确实能提升设计。私有方法和变量能强化信息隐藏，外部代码碰不到它们，就减少了依赖。但继承分成两种，影响完全不同。接口继承让父类只定义方法签名，子类各自实现不同版本，比如同一个I/O接口可以对接磁盘文件，也能对接网络套接字。这样一个接口就能服务多种场景，知识可以复用，接口也变得更深。实现继承则不同，父类不但定义签名，还给出默认实现，子类可以直接用或覆盖它。这能减少代码重复，缓解变更放大问题，不过它在父类和子类之间制造了紧密依赖。父类的实例变量常被子类访问，改动一个地方就得检查整个继承链，最坏情况下你得把整个层次结构都搞清楚才能动手。所以，实现继承要谨慎，最好先考虑组合方式，用小型辅助类共享功能，或者把父类和子类管理的状态分开，让信息隐藏真正起作用。

接下来是敏捷开发。它强调增量迭代，每个周期都添加功能、测试并收集反馈，这和我们提倡的逐步构建抽象很像。项目一开始不可能把复杂系统想得面面俱到，边做边重构才是正道。但敏捷有个风险，它容易把注意力拉到功能上，鼓励推迟设计决策，先做出能跑的东西再说。这就滑向了战术式编程，复杂性会快速堆积。正确的做法是把增量的单元定为抽象，而不是功能。一旦发现需要某个抽象，就花时间做好简洁设计，让它具备通用性。

单元测试现在已经很普遍了。程序员自己写小而聚焦的测试，覆盖单行代码或方法，还配合覆盖率工具检查。系统测试则由独立团队负责，确保整体协同。好的单元测试套件让重构变得安全，没有它，开发者就不敢大动结构，设计错误就一直留着。举个例子，Tcl脚本语言开发时，我们把解释器换成字节码编译器，这个改动几乎触及核心每一部分。幸亏有出色的单元测试套件，新引擎的缺陷在alpha版后只剩下一个。

测试驱动开发则要求先写测试再写代码。类还没实现，测试先失败，然后逐个让测试通过。表面上看很严谨，但我并不推崇它。它把焦点完全放在让功能跑通上，没有留出空间做整体设计，容易越做越乱。真正该先写测试的场景是修bug：先写一个能触发缺陷的测试，再修复并验证通过，这样才确认问题真的解决了。

设计模式提供了现成的解决方案，比如迭代器或观察者。在合适场景下直接套用，比从零发明要好。但风险在于过度使用，不是每个问题都非得套模式。强行套用只会让设计更复杂，只有模式真正匹配时才有效。

Java社区里Getters和Setters也很流行。它们包装实例变量，还能加额外逻辑，比如通知监听器或加约束。但公开实例变量本身就违反信息隐藏，Getters和Setters大多只有一行代码，却让接口变得更浅、更乱。最好从一开始就避免公开实现细节，而不是靠这些方法来补救。

带走的关键是：每遇到新的开发范式，都要从降低复杂性的角度去审视。很多听起来不错，深入看却可能适得其反。下一集我们将进入第20章，讨论如何在真实项目中持续应用这些原则。
