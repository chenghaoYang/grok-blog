# 第 4 集：模块应该是深的

欢迎来到《软件设计的哲学》有声博客。今天我们来聊聊软件设计里最核心的权衡之一：模块到底该怎么设计，才能真正降低系统的复杂性。管理软件复杂性最重要的技术之一，就是把系统拆成模块，让开发者在任何时候只需要面对其中一小部分。 [pause]

在模块化设计中，软件被分解成相对独立的模块集合。这些模块可以是类、子系统或者服务。理想情况下，每个模块都完全独立，你可以在一个模块里工作，完全不用了解其他模块。可惜现实中模块之间总有依赖关系：一个模块改了，另一个可能也得跟着改。模块化设计的目标，就是尽量减少这种依赖。为了管理依赖，我们把每个模块分成接口和实现两部分。接口告诉你模块能做什么，实现则藏着怎么做。在模块里工作的开发者需要知道自己模块的接口和实现，以及它调用的其他模块的接口，但不用管那些模块的内部实现。

模块的接口包含形式化信息和非形式化信息。形式化部分在代码里明确写着，比如方法的签名、参数类型、返回值。编程语言能帮你检查这些是否匹配。非形式化部分则包括高层行为和使用限制，比如某个函数会删除文件，或者调用顺序有要求。这些只能靠注释说明，语言无法自动验证。对大多数接口来说，非形式化部分比形式化部分更大更复杂。明确指定接口的好处，是它能准确告诉开发者使用模块需要知道哪些内容，避免“未知的未知”问题。

抽象和模块化设计紧密相关。抽象就是实体的简化视图，省略不重要的细节。它让我们更容易思考复杂事物。在模块化编程里，每个模块通过接口提供抽象。省略的细节必须真的不重要，否则抽象就会出错：要么包含多余细节让接口变复杂，要么忽略关键细节造成模糊。文件系统就是典型例子，它省略了磁盘块分配机制，但必须暴露数据何时真正写入存储设备，因为数据库这类应用需要确保崩溃后数据不丢。我们日常生活中也处处依赖抽象，微波炉和汽车都把复杂机制藏在简单按钮或方向盘后面。

最好的模块是那些功能强大却接口简单的模块，我称之为“深模块”。书里有一张图，把模块画成矩形，面积代表功能多少，顶部边长代表接口复杂度。深模块就像大矩形配短边，功能多但暴露的很少；浅模块则是小矩形配长边，功能不多却要学一堆接口。深模块有两个优点：简单接口能把强加给系统的复杂性降到最低，而且只要不改接口，内部修改就不会影响其他模块。

Unix 文件 I/O 是深模块的经典案例。它只有 open、read、write、lseek、close 五个基本系统调用，签名简单。open 接受路径名返回文件描述符，还能指定读写模式和权限；read 和 write 在内存和文件间传输数据；close 结束访问；lseek 支持随机定位。默认顺序访问最常见，随机访问通过 lseek 实现。现代实现有成千上万行代码，处理磁盘表示、目录查找、权限控制、缓存、设备合并等复杂问题，但这些对程序员完全不可见。多年来实现改了无数次，这五个调用却一直没变。垃圾收集器更极端，它甚至没有接口，在后台默默回收内存，却把释放对象的负担彻底拿掉。

反过来，浅模块会增加复杂性。实现链表的类就很浅，操作代码只需几行，接口复杂度却差不多高，学它几乎没省什么力气。一个把属性设为 null 的方法更是极端例子：调用者还得知道内部 data 变量，文档可能比代码还长，键盘敲击数也没少，却没提供任何抽象。Java 类库里打开文件要先建 FileInputStream，再包 BufferedInputStream，最后才到 ObjectInputStream，就是多类症的典型。每个类功能单一，结果累积出层层接口，反而让常见场景变麻烦。Unix 的做法是把顺序访问设为默认，需要时再用 lseek，常见情况最简单。

带走的核心原则是：设计模块时，优先让接口小而简单，同时提供强大功能，这样才能最大化隐藏复杂性。下一集我们将讨论如何在实际编码中进一步减少模块间的依赖关系。
